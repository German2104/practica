# AGENTS.md — факторный анализ Economic Capital и NPV

## Назначение проекта

Разработать прототип факторного анализа изменения Economic Capital (EC) и Net Present Value (NPV) между периодами `T0` и `T1`. Основной бизнес-кейс из постановки задачи — изменение NPV; аналитический метод должен допускать замену целевой метрики и набора признаков без переработки ядра.

Исходная постановка находится в файле `Постановка_задачи_Часть3_факторный_анализ_Economic_Capital.docx`. При расхождении примеров и требований сохраняйте проверяемое равенство: фактическое изменение метрики = сумма вкладов факторов и взаимодействий + необъясненный остаток. В примере документа изменение составляет `+15`, а перечисленные вклады дают `+11`; это нельзя выдавать за полное разложение.

## Архитектура

- Вход: CSV с наблюдениями за `T0` и `T1`.
- Аналитическое ядро: профилирование данных, сравнение моделей, расчет вкладов, взаимодействий, остатка и устойчивости.
- API: FastAPI или Starlette; интеграция Pydantic AI с интерфейсом через AG-UI и потоковые события SSE. Проверяйте API адаптера для фактически установленных версий библиотек.
- Интерфейс: чат, карточки факторов, графики зависимости и взаимодействий, состояние анализа и, где нужно, подтверждение пользователем.
- LLM: только интерпретация структурированного результата и ответы на вопросы о нем. Числа вычисляет аналитическое ядро.

Предполагаемый стек: `pydantic-ai`, `ag-ui-protocol`, `FastAPI`/`Starlette`, `scikit-learn`, `xgboost`, `shap`, `interpret`; для GAM допустим отдельный совместимый пакет. Не привязывайте аналитическое ядро к конкретной LLM или веб-интерфейсу.

## Данные и синтетический пример

CSV должен содержать как минимум `id`, `period`, целевую метрику (по умолчанию `npv`) и числовые либо категориальные признаки. Для демонстрационного кредитного портфеля используйте `volume`, `interest_rate`, `pd`, `ltv`; `lgd` и другие доступные характеристики поддерживайте как дополнительные признаки. Значения `period` — `T0` и `T1`. Проверяйте типы, пропуски, дубликаты ключей, соответствие наблюдений между периодами, выбросы и временную структуру. Не включайте целевую метрику или признаки, вычисленные из будущего периода, в обучающие факторы.

Генератор синтетического CSV должен создавать воспроизводимые данные за оба периода с известными пороговыми эффектами, насыщением или разными режимами и парными взаимодействиями. Пример из приложения: порог по LTV и совместный эффект LTV с PD. Сохраняйте истинную формулу генерации отдельно от результатов модели, чтобы проверять восстановление эффектов. Пример кода в приложенном тексте служит иллюстрацией, а не проверенной реализацией.

## Сравнение моделей

Сравнивайте на одинаковых разбиениях и одной целевой метрике:

1. Linear или Ridge — линейный базовый метод.
2. XGBoost с TreeSHAP — нелинейная модель и локальные вклады.
3. TreeSHAP interaction values — парные взаимодействия для совместимой древесной модели.
4. Explainable Boosting Machine (EBM) — интерпретируемые одномерные и двумерные эффекты.
5. GAM — дополнительная интерпретируемая модель для гладких нелинейностей.

Сохраняйте для каждого кандидата качество прогноза на отложенных данных, подписанный и абсолютный необъясненный остаток, устойчивость вкладов при временной проверке или бутстрэпе, способность обнаруживать известные нелинейности на синтетике и время работы. Не выбирайте модель по остатку на обучающих данных. Порог `stability_score > 0.85` из приложенной архитектуры используйте как настраиваемый критерий, а не как универсальную гарантию надежности. Если ни одна модель не проходит проверку, сообщайте, что надежное объяснение получить не удалось.

Различайте глобальную важность признака и его вклад в изменение метрики между двумя периодами. Для портфельного изменения согласуйте уровень агрегации наблюдений и базовые значения объяснений. Распределяйте взаимодействия по заранее описанному правилу, без двойного учета. Всегда проверяйте баланс вкладов с фактическим изменением целевой метрики; остаток храните со знаком. Для малых или нулевых изменений не используйте нестабильное отношение остатка к `ΔNPV` без отдельного правила.

## Этапы обработки

Названия ниже обозначают ответственности компонентов; отдельный LLM-агент для каждого этапа не обязателен.

1. `DataIngestionAgent`: загрузка CSV, валидация и профилирование данных.
2. `ModelBenchmarkAgent`: обучение и сравнение моделей на сопоставимых проверках, выбор подходящей модели.
3. `AnalyticalEngineAgent`: расчет изменения метрики, локальных вкладов, взаимодействий, остатка и диагностик надежности.
4. `LLMInterpreterAgent`: объяснение структурированного результата бизнес-языком и передача его через AG-UI.
5. `FactCheckerAgent`: проверка чисел и существенных утверждений до показа пользователю, включая потоковый вывод.

## Структурированный результат

Используйте валидируемые Pydantic-модели или эквивалентную строгую схему. Результат анализа должен включать:

- `target_metric`, `initial_value`, `final_value`, `total_change`;
- выбранную модель и результаты сравнения всех кандидатов: имя, качество, остаток, устойчивость, время работы и причину выбора;
- вклады факторов: имя, числовой вклад, тип эффекта (`linear`, `threshold`, `saturation`, `interaction`), пояснение и ссылку на расчет;
- взаимодействия: пару факторов, числовой вклад, описание и ссылку на расчет;
- подписанный `unexplained_remainder`, долю остатка, если она определена, уровень уверенности и ограничения;
- идентификаторы периода, версии данных, модели и метода атрибуции для воспроизводимости.

Проверяйте инварианты схемы: `total_change = final_value - initial_value` и `total_change ≈ сумма непересекающихся вкладов + unexplained_remainder` с явно заданным числовым допуском.

## Ограничения для LLM

- LLM получает только проверенный структурированный результат; не вычисляет NPV, EC и вклады самостоятельно.
- Каждое число и существенное утверждение в ответе должно быть связано с полем результата или диагностикой аналитического расчета.
- Если остаток ненулевой, показывайте его сумму и долю, когда доля корректно определена.
- При `stability_score < 0.70` предупреждайте о неустойчивости; при недостатке данных или провале проверок не формулируйте уверенное объяснение.
- Проверяйте потоковый текст перед показом числовых утверждений пользователю. Замена LLM не должна менять аналитические расчеты.

## Ожидаемый результат и проверки

Подготовьте описание методологии, работающий прототип, генератор и пример CSV, пример факторного разложения NPV, LLM-компонент, тесты и результаты проверок, сравнение с линейным базовым методом, анализ ограничений и рекомендации по развитию. Проверяйте решение на синтетических данных с известной формулой и на доступных реальных данных. Отдельно тестируйте пороги, насыщение, U-образные зависимости, взаимодействия, смену периодов, пропуски, нестабильные оценки и необъясненный остаток.

При разработке Python-кода следуйте локальному навыку `.agents/skills/python-clean-code/SKILL.md`, соразмерно масштабу задачи.

## Одна рабочая модель

По последнему указанию пользователя рабочий API и интерфейс используют одну
семью `stable_gam`, без переключения семейств. Настройки и проверки — ADR 0010.
Исследовательские сравнения исходного задания сохраняйте отдельно. Не выдавайте
высокий бутстрэп за прохождение всех критериев; неподтверждённые случаи должны
показывать отказ. Исторические исходники и результаты не заменяйте новой версией.
