# Python Clean Code

Пиши Python так, чтобы верхний уровень читался как сценарий, каждый класс имел понятную
ответственность, зависимости были видны, а изменения состояния происходили явно.
Основа — корпоративный `pylines-skill`, дополненный правилами модульного ООП, DI и пайплайнов.

Любую задачу сначала представляй как понятный путь от входа к результату: какие шаги нужны,
что делает каждый и как они связаны. Применяй это к API, CLI, расчётам, бизнес-операциям,
работе с данными и внутренним методам. Пайплайн здесь — способ организовать и читать код.

Это один самостоятельный скилл: установка исходного `pylines-skill` и доступ к сети для
его применения не нужны. Источник, командные соглашения и уточнения сохранены в
[references/pylines.md](references/pylines.md).

## Как выполнять задачу

1. Прочитай инструкции проекта, `pyproject.toml`, затрагиваемый сценарий и соседние тесты.
   Определи версию Python, существующий стек, публичные контракты и способ сборки зависимостей.
2. Выдели вход, результат, этапы обработки, внешние зависимости и точки изменения состояния.
   Сформулируй сценарий последовательностью смысловых действий с понятными переходами.
   Для небольшой задачи достаточно сделать это при чтении кода; отдельный дизайн-документ не нужен.
3. Реализуй минимальную законченную часть сценария. При рефакторинге сначала сохраняй
   наблюдаемое поведение, затем меняй внутреннюю структуру проверяемыми шагами.
4. Проверь изменённое поведение, типы и стиль средствами проекта. Устраняй относящиеся к
   задаче проблемы; ранее существовавшие ошибки обозначай отдельно.
5. Кратко сообщи, что изменилось, чем это проверено и какие ограничения остались.
   При запросе ревью выдай конкретные замечания с последствиями; файлы сам не переписывай.

Указания пользователя и действующие договорённости проекта определяют контекст применения.
Для нового проекта используй профиль pylines. В существующем проекте сохраняй совместимость
и принятый стек; миграция фреймворка, публичного API или всей конфигурации линтеров — отдельная задача.

## Классы и границы ответственности

- Не создавай файлы, состоящие из набора свободных функций для связанной прикладной
  логики. Оформляй такие операции в небольшие классы с одной ответственностью:
  публичный метод ведёт сценарий по этапам, приватные методы раскрывают детали,
  зависимости передаются явно через конструктор. Стремись к этой структуре и при
  изменении существующего кода: выделяй затронутый сценарий, не переписывая весь legacy.
- Предпочитай небольшие классы для компонентов с зависимостями, состоянием или несколькими
  связанными операциями. Класс должен иметь одну связную причину для изменения — SRP.
- Свободные функции оставляй для небольших чистых преобразований, composition root,
  тонких адаптеров фреймворка и pytest-тестов. Это исключение не оправдывает модуль
  из взаимосвязанных процедур или бизнес-логику в обработчике HTTP/CLI.
- Не заменяй модуль с функциями классом-контейнером из `staticmethod`: раздели
  ответственности и вырази реальный поток данных и эффектов. Не вводи интерфейс
  ради единственного внутреннего helper.
- Разделяй orchestration, предметные правила и I/O: сценарий определяет порядок действий,
  предметный код принимает решения, адаптеры работают с HTTP, БД и файлами.
- Используй композицию. Наследование оставляй для реального отношения подстановки или
  расширения, предусмотренного фреймворком. Не создавай `BaseService` и фабрики «на будущее».
- Внешние зависимости описывай небольшими `typing.Protocol` под потребителя, когда это
  отделяет сценарий от инфраструктуры или позволяет подменить адаптер в тестах.
- Реальные варианты поведения выноси в стратегии. Простой устойчивый `if` не требует
  реестра обработчиков или нового паттерна.
- Сохраняй структуру проекта. Выделяй модули по задачам и границам; не навязывай один файл
  на класс, много пустых слоёв и формальные лимиты количества строк.

## Явные зависимости и жизненный цикл

- Передавай зависимости через именованные параметры конструктора или поля dataclass.
  Для подходящих компонентов используй `@dataclasses.dataclass(kw_only=True, slots=True, frozen=True)`.
- Собирай граф объектов в composition root: точке запуска, lifespan, фабрике приложения
  или уже существующих DI-провайдерах. Обычная передача аргументов — полноценный DI.
- Конструктор сохраняет зависимости и проверяет локальные инварианты. Подключение к сети,
  создание таблиц и коллекций, загрузку файлов выполняй отдельным этапом.
- Не создавай инфраструктурные клиенты внутри бизнес-методов. Не доставай зависимость из
  соседнего сервиса через `getattr`, глобальный service locator или скрытый fallback.
- Возвращай из сборки готовый к использованию объект. Избегай циклической сборки через
  `Service(None, None)` с последующим присваиванием обязательных зависимостей.
- Определи владельца клиента, пула, executor и фоновых задач. Создание, закрытие и отмена
  принадлежат явному жизненному циклу; используй context manager или `try/finally`.
- DI-контейнер добавляй при реальной сложности scopes и сборки либо используй уже принятый.
  Для небольшого графа достаточно функции сборки.

## Методы, которые читаются сверху вниз

- Верхний метод выражает сценарий: получить → проверить → преобразовать → сохранить.
  Детали шагов располагай ниже или в соответствующих компонентах — Stepdown Rule.
- При проверке MR просмотри весь изменённый Python-сценарий, включая добавленные ранее
  коммиты. Проверь границы классов, явный DI и последовательность этапов; успешный
  линтер сам по себе не подтверждает такую архитектуру.
- Выдерживай один уровень абстракции в методе. Не смешивай «проиндексировать документ»
  с конструированием SQL, очисткой временной папки и разбором HTTP-ответа.
- Выделяй метод, когда появляется самостоятельный смысл, граница эффекта или повторяемая
  операция. Дробление каждой строки на отдельный метод добавляет переходы, но не обязательно
  улучшает понимание. Оценивай читаемость сценария, а не количество строк в методе.
- Используй early return и guard clauses. Промежуточная переменная полезна, если даёт
  имя значимому результату или устраняет повторный расчёт.
- Называй действие конкретным глаголом. `check_*`, `is_*` и `has_*` не должны незаметно
  сохранять файлы, обновлять статусы или публиковать события.
- Предпочитай явные `run_pipeline`, `process_document`, `fetch_document` вместо скрытого
  `__call__(*args, **kwargs)`. Существующий контракт фреймворка сохраняй.

## Контракты и Python-стиль

- Аннотируй параметры, результаты и состояние объектов; стремись к `mypy --strict`.
  На границах валидируй вход; внутри работай с конкретными DTO и типами.
- Для новых собственных переменных и функций профиль pylines требует содержательные имена
  длиной от 8 символов. Исключения: `self`, `cls`, специальные методы и обязательные внешние
  сигнатуры. Не переименовывай чужой API и не дополняй имя бессмысленными символами.
- `get_*` оставляй для чтения из памяти; для I/O используй `fetch_*`, `load_*`, `download_*`.
- Для привязок без переназначения применяй `typing.Final`; выводимые скалярные типы не
  дублируй. Конкретные классы по умолчанию помечай `@typing.final`, если расширение не нужно.
- `Final` не делает объект неизменяемым; `frozen=True` не замораживает вложенные коллекции.
  Детали допустимой изменяемости и исключения для Protocol описаны в reference.
- Используй dataclass для внутренних данных, Pydantic/msgspec на границе при необходимости
  валидации, `TypedDict` для структурированных словарей, `Literal`/Enum для конечных наборов.
- Не передавай по цепочке `dict[str, Any]`, строковые флаги и `None` с несколькими значениями.
  Типы этапов должны показывать, какие данные уже доступны. Избегай и DTO на каждую мелкую операцию.
- Стандартную библиотеку импортируй модулями: `import dataclasses`, `import typing`.
  Более двух имён из одного модуля — повод импортировать модуль целиком.
- Комментарий объясняет причину или ограничение; docstring — полезный контракт. Не пересказывай код.

## Любой сценарий как пайплайн

- Начинай проектирование с верхнего сценария: по его коду должно быть понятно, что
  произойдёт от входа до результата, без чтения реализации каждого шага.
- Сценарий управляет порядком и переходами, этап выполняет одну смысловую работу.
  Например: регистрация — проверить данные → создать учётную запись → сформировать ответ;
  расчёт — подготовить значения → применить правила → собрать результат.
- Уточняй шаги сверху вниз: сложный этап раскрывается в собственную последовательность
  понятных действий. На каждом уровне сохраняй одинаковый масштаб детализации.
- Выражай ветвления, циклы, параллельные действия, переходы состояний и ранний выход явно.
  Они являются нормальной частью сценария. Сохраняй реальный поток управления;
  последовательность вызовов не должна искажать зависимости шагов.
- Обычного метода с вызовами функций или компонентов достаточно. Выделяй класс сценария
  при наличии связных операций и зависимостей; название `Pipeline`, базовый `Step`
  и универсальный движок не требуются.
- Граница метода сама по себе не делает шаг независимым. Если шаги незаметно меняют
  общий `self.context`, их порядок становится хрупким, даже когда методы короткие.
  Предпочитай явные аргументы и результаты, передавая минимальные нужные данные.
  Если общее изменяемое состояние необходимо по смыслу задачи, делай его переходы явными.
- Если вызывающей стороне важно различать успех, пропуск и ошибку, вырази эти исходы
  типом результата или конкретными исключениями. Не добавляй `Result`-обёртку везде автоматически.
- Возвращай результат шага после выполнения обещанного действия. Если контракт шага
  включает сохранение, оно должно успешно завершиться до возврата успеха.

## Ошибки и ресурсы

- Разделяй ошибки данных и временные отказы инфраструктуры. Лови конкретные исключения
  в узком `try`; сохраняй причину через `raise ... from error` при переводе между слоями.
- `except Exception` допустим на внешней границе приложения, если есть явная политика обработки
  и сохранён traceback. Не превращай неожиданный сбой в молчаливый `False` или «успех».
- Retry ограничивай попытками/временем, timeout и backoff с jitter. Повторяй только
  подходящие временные сбои при безопасном повторном выполнении операции.
- Не блокируй event loop синхронным I/O. Используй async-клиент или подходящий executor;
  для тяжёлого CPU-этапа отдельно выбирай модель выполнения.
- Закрывай ресурсы при успехе и ошибке. Для асинхронного сценария также обрабатывай
  timeout/cancellation и завершай принадлежащие ему задачи.
- Логи должны позволять найти запуск, объект, этап и причину сбоя. Не логируй секреты
  или содержимое документов целиком по умолчанию.

Для проектирования нового сценария или выделения его этапов прочитай
[references/pipeline-example.md](references/pipeline-example.md): там показаны границы,
сборка через DI и последовательные изменения без универсального движка пайплайнов.

## Проверка результата

- Проверяй поведение и инварианты: корректный результат, ветвления, граничный ввод
  и отказ зависимости — когда эти случаи относятся к изменению.
- Для сервисного сценария предпочитай интеграционный тест. Чистые правила и преобразования
  удобно проверять небольшими unit-тестами без мокирования внутренних методов.
- Используй AAA и параметризацию; Faker/Hypothesis — когда вариативность помогает найти ошибки.
  Для известного граничного случая оставляй фиксированный воспроизводимый пример.
- Запускай существующие проверки проекта. При новом tooling, тестовой инфраструктуре,
  REST API или выборе библиотек прочитай соответствующий раздел
  [references/pylines.md](references/pylines.md).
- Не создавай тест, проверяющий только число классов, наличие декоратора или порядок
  вызовов приватных helper'ов. Не добавляй тесты ради косметической правки.

Перед сдачей проверь: сценарий понятен сверху вниз; ответственность и зависимости видны;
имена соответствуют эффектам; контракты типизированы; успех означает завершённую работу;
ошибки и ресурсы имеют владельца; проверки соответствуют риску изменения.
